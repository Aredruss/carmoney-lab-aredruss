# Plan: добавить комментарий в `backend/public/index.php`

## 1. Файлы

- `backend/public/index.php` — добавить одну строку комментария (содержание — см. «Шаги» и «Вопросы»).
- Только этот файл. Больше ничего не трогаем. `config/`, `src/`, `tests/`, `db/`, `docs/setup/code_map.md`, `composer.json`, `docker-compose.yml`, `Makefile` — не меняем.

## 2. Шаги

1. Прочитать `backend/public/index.php` целиком (9 строк). Подтверждено: `<?php`, `declare(strict_types=1);`, `use CarMoneyLab\AppFactory;`, `require …/vendor/autoload.php;`, `AppFactory::create()->run();`. Больше ничего нет.
2. Согласовать с заказчиком **текст** комментария (см. «Вопросы») — без этого шага план нельзя закрыть.
3. После согласования — вставить комментарий на место по решению заказчика:
   - вариант A — заголовок файла, строка после `<?php` (перед `declare(strict_types=1);` или после `declare` и пустой строки), в виде PHPDoc-блока `/** … */`;
   - вариант B — поясняющая строка перед `require …/vendor/autoload.php;` (назначение точки входа и почему именно `AppFactory::create()->run()`);
   - вариант C — поясняющая строка перед `AppFactory::create()->run();` (что именно стартует — HTTP-приложение Slim, см. `docs/setup/code_map.md:13`).
4. Файл остаётся синтаксически валидным PHP 8.3: `declare(strict_types=1);` сохраняется как первая инструкция после `<?php`. Если комментарий идёт перед `declare`, синтаксис не ломается (PHP допускает комментарии перед `declare`); если после — тоже.
5. (опционально) прогнать `php -l backend/public/index.php` (через `make lint` или напрямую) — подтверждение синтаксиса, без запуска тестов и без перезапуска контейнеров.

## 3. Тесты

- Новых тестов не добавляем: задача — только комментарий, поведение не меняется.
- Существующий `tests/` не затрагивается. `make test` по сравнению с предыдущим прогоном должен давать тот же результат.
- Граничные случаи, которые нужно не забыть:
  - PHPDoc-блок с `*/` внутри текста — должен быть экранирован или заменён многострочным комментарием без вложенного `*/`;
  - кодировка — UTF-8 без BOM; русский текст допустим (репозиторий уже содержит RU-комментарии в `code_map.md`).

## 4. Риски

- **Содержание, а не синтаксис — главный риск.** Произвольно выдуманный комментарий может противоречить фактическому поведению (`AppFactory::create()` собирает не «консольное», а HTTP-приложение Slim — см. `docs/setup/code_map.md:13`). Поэтому без согласования с заказчиком план не исполняем.
- Синтаксические риски минимальны: PHPDoc-блок и `//` в любом месте файла валидны.
- Соседние файлы не задеваем, поэтому регрессий в `AppFactory`, `AssessmentService`, валидаторе, LTV-калькуляторе и `DecisionEngine` не ожидается.
- Вне рамок: правила в `backend/config/rules.php`, формулы в `LtvCalculator`, поведение `DecisionEngine`, `max_mileage_km`, тесты на пробег, документация в `docs/setup/code_map.md`, `docs/sources/` — всё это **не** меняется этой задачей.

## Вопросы (без ответов план не закрыть)

1. **Текст комментария.** Что именно должно быть написано? Варианты, между которыми надо выбрать:
   - (a) краткое описание точки входа HTTP — что это фронт-контроллер Slim-приложения из `AppFactory`;

2. **Стиль комментария.** PHPDoc `/** … */` (рекомендуется для файловой шапки) или однострочный `// …` (легче поддерживать)?
3. **Расположение.** Шапка файла (после `<?php` / `declare`) или поясняющая строка непосредственно перед конкретной инструкцией (`require …`, `AppFactory::create()->run()`)?
4. **Язык.** Русский (как `docs/setup/code_map.md` и комментарии в коммитах) или английский (как PHPDoc в `backend/src/Domain/`)?
