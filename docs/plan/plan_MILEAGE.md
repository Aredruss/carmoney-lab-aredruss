## 3. Тесты

`tests/Unit/AssessmentServiceTest.php` (пробег задаётся через `payload()`, остальные поля —
валидная заявка; LTV-зона регулируется суммой/стоимостью):

- пробег 399999 (LTV 50, зона approve) → `approve`, `approved_limit` = запрошенной сумме — правило не сработало (AC-MILEAGE-01);
- пробег 400000 (LTV 50) → `approve`, `approved_limit` = запрошенной сумме — граница включительна по допущению OQ-1 (AC-MILEAGE-02);
- пробег 400001 (LTV 50) → `review`, `approved_limit` = 0 — правило сработало;
- пробег 500000 при LTV 50 (верхняя граница валидации) → `review`, `approved_limit` = 0 — накрывает весь диапазон действия правила 400 001–500 000 (AC-MILEAGE-04);
- пробег 400001 при LTV 95 (зона reject) → `review` — буквальное чтение; тест фиксирует открытое допущение OQ-3 спеки, при ответе «не смягчать» ожидание меняется на `reject` (AC-MILEAGE-10);
- пробег 400001 при LTV 75 (уже review) → `review`, `approved_limit` = 0 — правило идемпотентно для review.

`tests/Unit/ApplicationValidatorTest.php` (код валидатора не меняется):

- пустой пробег — поле `mileage` отсутствует → `ValidationException` с ключом `errors['mileage']`, заявка не доходит до решения (AC-MILEAGE-07);
- пустой пробег — `mileage => null` → тот же `ValidationException` (`?? -1` даёт −1; AC-MILEAGE-08);
- пустая строка `mileage => ''` → валидатор приводит её к 0 и пропускает заявку — фиксация текущего поведения (рабочее допущение OQ-2 спеки, AC-MILEAGE-09);
- пробег −1 → `ValidationException` — нижняя граница валидации (AC-MILEAGE-06);
- пробег 500001 → `ValidationException` — верхняя граница `max_mileage_km` (AC-MILEAGE-05): такие заявки отсекаются валидацией и до нового правила не доходят — закрытый вопрос OQ-4 спеки (ответ заказчика в интервью, вопрос 4).

## 4. Риски

- **`max_mileage_km` (500 000) — главный соседний риск.** Новое правило реально действует
  только на 400 001…500 000: пробег свыше 500 000 отсекается валидацией с 400-ошибкой
  и до решения не доходит (`code_map.md:47`) — это закрытое решение заказчика (OQ-4
  спеки, интервью 2026-09-24, вопрос 4). Менять `max_mileage_km` ради «зелёного»
  поведения нельзя без решения риск-владельца (AGENTS.md). Также важно не спутать
  два порога при реализации: `max_mileage_km` — граница валидации, `review_mileage_km` —
  граница решения.
- **Семантика против `reject`.** Буквальное чтение превращает и `reject` по LTV в `review`
  при пробеге > 400 000, т. е. смягчает отказ. В материалах LOAN-12 (П-5) фактор может
  «только ужесточать решение, но не смягчить», а очередь андеррайтеров перегружена уже
  при 60 заявках (`CONF-underwriting-queue`). Рабочее допущение спеки (OQ-3) —
  буквальное чтение, владелец вопроса — бизнес-аналитик. Если он подтвердит
  «не смягчать» — правка одна строка, но она должна быть сделана осознанно.
- **Связка с `approved_limit`.** Лимит считается из `$decision === APPROVE` в том же
  `return`. Проверка обязана стоять до сборки ответа (шаг 3); если её перенести ниже —
  `review` получит ненулевой лимит. Страховка — ассерт `approved_limit === 0` в тестах на review.
- **Рябь конструктора.** `AssessmentService` собирается ровно в двух местах:
  `AppFactory.php:30–39` и `AssessmentServiceTest.php:24–29`. Оба меняются в одном
  PR; пропуск любого — падение сборки/тестов. Отсутствие ключа в `rules.php` роняет
  тесты сразу (`undefined array key`) — fail-fast, приемлемо.
- **Сборка через `AppFactory` не покрыта тестами** (Feature-тестов нет): неверная
  передача порога в фабрике юнит-тестами не ловится, проверяется вручную (шаг 6)
  или будущими Feature-тестами.
- **Коэрцция пустой строки.** `''` → 0 проходит валидацию как «нулевой пробег» —
  существующий кварк валидатора. План его фиксирует тестом, но не чинит: правка
  `ApplicationValidator` вне списка файлов и без ответа на открытый вопрос OQ-2
  спеки (владелец — системный аналитик) невозможна.
- **Существующие примеры не ломаются.** Все известные фикстуры и примеры — 8 400 /
  20 000 / 84 000 / 96 000 / до 320 000 км (тесты, seed, README, таблица LOAN-12) —
  ниже порога, их исходные решения не меняются.
- **Не трогаем чужое расхождение.** В `DecisionEngine` докблок обещает `LTV <= approve_max`,
  а код использует строгое `<` (`code_map.md:17`). Это не наша задача — не «чиним»
  молча: смена сравнения меняет решение при LTV ровно 60 и требует вопроса риск-владельцу.
- **Что не входит:** изменение `max_mileage_km`, логики и сообщений `ApplicationValidator`;
  сигнатуры и поведения `DecisionEngine` и `LtvCalculator`; влияние пробега на LTV или
  лимит; возрастные лимиты LOAN-12; журнал решений LOAN-15 и маркировка причин review;
  скидки за пробег из CASE-08; фронтенд, БД (`schema.sql`/`seed.sql`), репозиторий,
  HTTP-слой, `Makefile`, `docker-compose.yml`.
